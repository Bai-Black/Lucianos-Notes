# 前置知识

## 运行时 Runtime

根据语境不同，Runtime 可能有很多种含义。

### 1.程序运行的阶段

更严谨地说是 **Run Time **，与 **编译时（Compile Time）**相对应。

举例来说，我们常把程序的错误分为运行时错误和编译时错误。

- 编译时错误

  ``` C
  int* a = 1.14f;
  ```

  在编译阶段就会报错，无法编译为二进制文件。

- 运行时错误

  ``` C
  int* a = (int*)0xCAFEBABE;	//一个不存在的地址
  *a = 114;
  ```

  可以编译为二进制文件并运行，但在运行时会因为无法找到地址而报错。

显然，运行时错误的成因更加复杂，排查难度远大于编译时错误。

### 2.**运行时环境 Runtime Environment**

> **重点含义**

**指程序从开始执行到结束运行这一阶段所处的整个环境，以及支撑程序运行所需要的机制和资源。**

这是非常广的概念，又可以通过其“大小”继续细分：

#### 2.1 运行时库 Runtime Library

编译型语言被设计为既可以开发运行在操作系统上的原生程序，又可以开发裸机程序。在开发前者时，对于频繁调用的底层系统接口和部分机器码指令，封装成二进制库，供程序调用。它一定会被被动态编译或静态编译到最终程序，尽管你的代码没有 include 它。

主要提供**程序启动和退出**，以及与操作系统连接的**内存管理**、**文件IO**等底层功能。

> 典型代表如 C语言 的 **CRT(C Runtime Library)** 。

#### 2.2运行时系统 Runtime System

运行时库总体来说是轻量级的，仅包含一些底层功能。而当运行时环境进一步膨胀，加入解释某种字节码等功能，成为一个软件，乃至一个虚拟机时，就可以称之为**运行时系统（Runtime System）**。

> 典型代表如 Java 的 JRE 。

#### 2.3 更小的运行时

运行时库的规模可以进一步缩小（但不可能缩小到没有，任何程序都有运行时），仅仅保留能使 CPU 执行用户代码的最基本流程。这种情况下，由于 Runtime 没有了线程调度、进程管理、文件系统等操作系统的基本功能，不再认为是完整的操作系统。在这种 Runtime 下开发的程序，就是裸机程序。

## 终端 Terminal  &  控制台 Console  &  Shell

> 现代的一般语境中没有必要区分得那么清楚，这里作拓展阅读。

### 控制台 Console

早期计算机中，Console 指能实时直接与内核通信的，进行0/1输入输出的设备，如键盘。此后，Console 在事实上衍变为一套特殊的，供管理员使用的 Terminal 。

特点：

- 面向管理员，具有特殊权限
- 与内核关系更直接

---

### Shell

Shell ，即**外核**，与系统**内核（Kernel）**对应。在早期就是内核之上对于多个流封装和抽象并加入了ASCII/Unicode字符解码。负责解析命令、调用系统 API、启动程序等实质工作。

如 Windows 有 cmd、PowerShell 两种 shell ; macOS 可以使用 bash、zsh、fish。

是 Terminal 与内核间的桥梁。

---

### 终端 Terminal

早期计算机中的 Terminal 指的是物理终端设备，当时个人用户无法负担计算机，于是大型计算机通过多个终端设备供多人使用。用户通过 Terminal 连接主机、输入命令、查看结果。

现代操作系统中的终端本质上是**模拟传统硬件终端的软件**，即**终端模拟器（Terminal Emulator）**，简称为终端。它只负责显示文字、接受输入等表层交互，并传递给 Shell 。

如 Windows 中的 Windows Terminal 。cmd 与 PowerShell 都是通过该程序进行交互，因此外表看上去一样。

---

## 环境变量 & Path

**环境变量**是一组变量，由操作系统提供给运行的程序。

常见的环境变量如 **TEMP** ，程序读取该变量即获得存储临时文件的地址。

---

**Path** 是最重要的环境变量之一，保存的是可执行程序 (exe) 的存储地址。

例如，当安装 python 时，需要把安装目录添加到 Path 。

从而，当在命令提示符运行：

``` cmd
python test.py
```

系统会自动在 Path 变量包含的所有目录内寻找 python.exe 。

同理，CMake、git、pip等程序也会将自己的目录加入 Path 。

---

总结：**只有需要被别人找到的东西，才需要配置环境变量**

- 若一个程序希望在任何终端直接输入名字运行，则加入 Path 。(Python, git...)
- 若希望其他程序知道它的安装位置，则设置专用环境变量。(JAVA_HOME, CUDA_PATH...)

# 开发环境概述

完整的开发环境由如下几个层级组成：

## 第一层：指令集架构与操作系统

**指令集架构**（如x86、Arm）定义处理器能够执行的指令、寄存器及程序可见的机器模型。在一台计算机设备上，任何软件想要被执行，必须转换为**该计算机架构**对应的**指令序列**。

**操作系统**（更准确地说是**操作系统内核**，而不包括 shell 等外围）负责文件系统、内存管理、进程、权限等底层。普通程序最终都是由操作系统加载运行。

在通用软件软件开发中，常将 **指令集架构 + 操作系统** 的组合称为目标**平台**，作为编译和分发二进制程序的基本分类。

---

---

## 第1.5层：ABI

> 严格来说并不能算一个层级，因为这只是一种**规则**，而非实质性组件。

**ABI（Application Binary Interface）**位于同一平台上的**二进制模块**之间，描述“编译后的二进制模块如何连接、交换数据和互相调用”。它可以视为一种**规则**，而非实际完成了任何工作。**语言实现**遵守相应的 **ABI 规则**，将语言转换为可供目标**平台**执行的二进制代码。

对于不同的平台与语言间的组合，平台先提供基础ABI，通常规定：

- 基本调用约定
- 寄存器使用
- 栈对齐
- ······

例如：

``` 
Linux x64   -> System V AMD64 ABI
Windows x64 -> Microsoft x64 ABI
```

在此基础上，语言针对自身特性需求，可能在平台ABI之上增加规则。如 C++ 需要表达命名空间、类等特性，Windows 上的 C++ 编译通常遵守 `Microsoft x64 ABI + Microsoft C++ ABI`。

- 同一种语言可能有多个 ABI。如 Windows 上的 C++ 除了 `Microsoft C++ ABI`，还有 `GNU/Itanium体系`。
- 一种语言可能没有自身的稳定 ABI 。如 Rust 内部 ABI 不承诺跨 Compiler 版本稳定，从而需要长期稳定的预编译库接口通常改用 C ABI。
- 可以使用其他语言的 ABI ，在明确支持的情况下。
- 多种语言可以共享同一个 ABI 。如 C/C++/Rust 通常共享 C ABI

**C ABI** 是各个平台上最常用的跨语言 ABI 形式，这是由 C语言 的特殊性决定的：

- C语言的接口模型简单，它的各种概念直接与硬件层面高度对应，是各种高级语言的“最大公约数”
- 操作系统与芯片生态长期使用 C ，形成巨大的历史积累
- 汇编容易实现 C 函数

---

---

## 第二层：语言实现

不同语言的实现方式不同，大致可以通过**运行时**的“大小”，分为三类**（不严格）**：

### 编译型语言/系统级语言

> **轻量化**运行时库，或者更小，与底层直接连接的语言，如C、C++、Rust

需要：

**源码 	-> 	编译/汇编	 -> 	目标文件	 -> 	链接 	-> 	可执行文件/库**

源码会被编译为操作系统对应的可执行文件，直接运行。

 **特点：**

- CPU直接执行，速度快
- 但不同平台和 ABI 通常需要分别构建。

---

### 解释型语言/高级语言

> **中量级**运行时系统，如Python、JavaScript

流程：

**源码	->	字节码	->	解释器**

真正运行的程序是解释器，如python.exe

**特点：**

- 由解释器程序执行代码

---

### 虚拟机语言/高级语言

> **重型**运行时系统，如Java、C#

可以看作前两种方案的折中，Java 的设计者提出：

> 先编译一次，但不要编译为机器码，而是在所有平台通用的中间语言。

流程：

**源码	->	编译器	->	字节码	->	虚拟机**

相较于解释器直接解释高级语言源码，虚拟机（如 JVM(Java Virtual Machine)）执行一种专门设计的中间指令集（字节码），并通常包含 JIT 编译、垃圾回收、内存管理、线程调度等完整运行时系统，成为一个功能完整的运行时系统。这也是为什么 Java、C# 等语言能够提供跨平台、自动内存管理和较高运行性能。

---

---

## 第三层：构建系统与构建器

是 **源码** 与 **语言实现** 的桥梁，定义了整个项目的源码与语言实现如何对接，从而编译/运行。

> 典型如 CMake 生成构建规则，Ninja 执行规则。

---

---

## 第四层：源码与依赖

项目层面包括自身源码与依赖。依赖可能以源码、头文件、静态库、动态库或运行时组件的形式提供。

**第三方库**依赖如：C++的**OpenCV**, **Qt**、Python的**NumPy**

> API（Application Programming Interface）位于源码模块之间，描述“代码应该怎样调用另一个模块”。包括函数名、参数、返回值和使用规则。
>
> 与 ABI 的对比：
>
> |      | 对象           | 遵守者                   |
> | ---- | -------------- | ------------------------ |
> | ABI  | 二进制模块接口 | 编译器、链接器和汇编代码 |
> | API  | 源码接口       | 程序员/源码编写者        |

# 单语言项目的环境管理

下文的“环境”主要针对第二、三、四层，包括**编译器/解释器、SDK、依赖库及其版本，以及这些组件的组织方式**，以项目为单位进行管理。

本节致力于针对各语言在**环境管理**方面，整理出一套**现代、高效、标准化、易于统一**的工作流。

不同语言有不同的成熟度，有的语言有几乎统一的管理工具，有的语言的编译、构建、包管理高度独立。

## Python

随着 `uv` 的发展，Python 的环境管理正向一体化靠拢。它把过去分散在 `venv`、`pip`等多个工具中的职责尽可能整合到一个统一的工作流中。

### 相关文件

#### `pyproject.toml`

Python 官方定义的通用的项目信息文件，包含了其所需的 Python 版本、依赖列表等信息。绝大多数工具已经添加了对该文件的支持。

``` 
[project]
name = "python-test"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.14"
dependencies = []
```

可以手动编辑该文件，修改项目名称、版本、描述等信息。项目依赖列表( dependencies )一般通过其他工具（`uv`）管理。

---

#### `.python-version`

由 `uv` 创建。

包含项目的默认 Python 版本。此文件告诉 uv 在创建项目虚拟环境时要使用哪个 Python 版本。

需要注意的是，`pyproject.toml`文件中声明的是项目支持的 Python 版本，而本文件规定具体使用哪个解释器。

---

#### `uv.lock`

`uv` 创建的跨平台锁定文件，包含依赖项的精确信息。

由 `uv` 管理，不应手动编辑。

---

#### `.venv`

该文件夹包含项目的虚拟环境，这是一个与系统其他部分隔离的 Python 环境。若使用 VS Code 等编辑器，应当将环境选择在这里。

---

---

## C/C++

> 史

C++ 没有统一工具。

一个 Python 项目的环境，通常可以概括为：

> Python 解释器版本 + Python 依赖版本

而一个 C++ 项目的构建环境至少包含：

> 操作系统 + CPU 架构 + 编译器工具链 + C++ 标准 + 构建类型 + 第三方库及其构建选项

例如，同一个第三方库使用 MSVC 和 GCC 编译，或者分别为 x64 和 ARM64 编译，得到的二进制文件通常不能混用。即使平台和编译器相同，Debug、Release、静态链接、动态链接等选项也可能影响二进制兼容性。

因此，C++ 的环境管理不是由单一工具完成的，而是由以下三部分共同组成：

1. **编译工具链**：把源代码转换为特定平台的二进制文件。
2. **构建系统与构建器**：组织编译目标，并调用工具链完成构建。
3. **包管理器**：获取、构建和管理第三方依赖。

---

### 编译工具链

编译工具链负责把 C++ 源代码转换为操作系统能够加载的程序或库。

通常经历以下阶段：

```text
源文件
  ↓ 预处理
翻译单元
  ↓ 编译
汇编代码
  ↓ 汇编
目标文件
  ↓ 链接
可执行文件或库
```

**编译器驱动程序**根据参数依次调用预处理器、编译器、汇编器和链接器，因此一个简单程序可以用一条命令完成构建。

常用的**编译器驱动程序**有 `MSVC` 的 `cl`、`GCC` 的 `gcc/g++`、`Clang` 的 `clang++` 。

---

#### GCC (GNU Compiler Collection)

**GCC** (GNU Compiler Collection)，即 **GNU 编译器集合**。编译C/C++程序使用的 gcc/g++ 只是其中的两个。GCC 同时还包括 Fortran、Ada、Go 等语言的支持。

> **GNU** 是1983年 Stallman 发起的开源运动，所有GNU软件都有一份在禁止其他人添加任何限制的情况下授权所有权利给任何人的协议条款，**GNU通用公共许可证**(GNU General Public License，**GPL**)。

> **Linux 内核**编写完毕后，与大量**GNU软件**（包括GCC）结合，成为 **Linux 操作系统**。

总结：GCC 作为一个编译器集，是 Linux 操作系统的一部分。

优点：

- Linux 生态优势
- 稳定
- 目标平台广

不足：

- 工具链分散
- 错误信息难阅读

##### MinGW (Minimalist GNU for Windows)

MinGW 使得 Windows 平台可以使用 GCC .

MinGW-w64 是其增强版本，支持64位程序，是常用版本。

MSYS2 提供 Unix-like 环境和包管理，类似 Linux 终端。

---

#### MSVC (Microsoft Visual C++ Compiler)

MSVC 是 Microsoft 提供的 C/C++ 工具链，主要用于 Windows 开发。

常见组件包括：

- `cl.exe`：编译器驱动程序；
- `link.exe`：链接器；
- Microsoft C++ 标准库；
- MSVC 运行库；
- Visual Studio Debugger；
- 与 Windows SDK 配合使用的头文件和库。

优点：

- Windows 生态最佳
- 调试体验最佳
- ABI稳定

> ABI (Application Binary Interface) 决定不同编译器生成的二进制是否兼容。通常 C 接口可以相互兼容，而 C++ 接口可能有风险。

---

#### Clang

**Clang** 是基于 LLVM 的 C/C++/Objective-C 编译器前端。

> LLVM (Low Level Virtual Machine（历史名称）)，现多指译器基础设施平台。其核心思想是建立一个编译中间层：LLVM IR，类似一种“编译器通用语言”。同一个 IR ，可以生成不同平台的机器码，作为编译链的后端。

Clang 是LLVM 的 C++ 语言前端，将 C++ 源码转译为 LLVM IR。而 LLVM 同时支持更多语言的前端，包括 Rust、CUDA。这样的模块化设计体现了它的现代。苹果早早布局 LLVM，苹果生态都深度依赖 LLVM，这也是为什么 macOS 使用 Clang.

优点：

- 更好的诊断
- 更现代的 C++ 支持
- 静态分析工具丰富
- 跨平台一致

##### clang-cl

**clang-cl** 是 Clang 的 MSVC 兼容模式，即 Clang + MSVC 接口。

普通 Clang (Clang++) 是 GNU 风格，clang-cl 是MSVC风格。

clang-cl 与 MSVC 中的 cl 是平行关系，即替代了其编译器驱动程序为 Clang 内核。

在 Windows 平台上，这结合了 Clang 与 MSVC 二者的优点。

### 构建系统与构建器

当项目只有一个源文件时，可以直接调用编译器。随着项目扩大，还需要解决以下问题：

- 管理大量源文件和头文件；
- 只重新编译发生变化的部分；
- 描述可执行程序与库之间的关系；
- 管理 Debug、Release 等构建配置；
- 在不同操作系统和编译器之间复用项目配置；
- 查找和链接第三方依赖；
- 运行测试、安装和打包。

这些职责由构建系统与构建器承担。

#### CMake 基本使用

综上介绍，现代工程常使用 CMake + Ninja 组合。下面介绍 CMake 使用。

##### 安装<a id="cmake-install"></a>

进入[官网](https://cmake.org/download/)，下载`Windows x64 Installer`。运行。

需勾选添加至 PATH：

<img src="images/image-20260724165855265.png" alt="image-20260724165855265" style="zoom:50%;" />

##### 工作流概述

一个典型项目：

```
MyProject
│
├── CMakeLists.txt
│
├── src
│   ├── main.cpp
│   └── math.cpp
│
├── include
│   └── math.h
│
└── build
```

流程：

```
CMakeLists.txt
        |
        |
        ↓
      CMake
        |
        |
        ↓
生成构建系统
        |
 ┌───────────────┐
 │               │
Ninja          MSBuild
 │               │
 ↓               ↓
clang++        cl.exe
 │
 ↓
程序
```

##### 核心文件`CMakeLists.txt`

最小实例：

```cmake
cmake_minimum_required(VERSION 3.20)

project(Hello)

add_executable(
    hello
    main.cpp
)
```

- `cmake_minimum_required`：指定最低 CMake 版本
- `project`：定义项目。只带一个参数则视为项目名。

##### Target思想

Target就是：

- 可执行文件
- 静态库
- 动态库

不使用全局变量，而是Target属性，只影响Target本身。

```cmake
add_executable(
    app
    main.cpp
)
```

生成：`app.exe`

##### 添加头文件路径

老方式，全局：

```
include_directories(
    include
)
```

现代方式：

```
target_include_directories(
    app
    PRIVATE
    include
)
```

##### 静态库

```cmake
add_library(
    math
    STATIC
    math.cpp
)
```

生成：`math.lib`

##### 动态库

```
add_library(
    math
    SHARED
    math.cpp
)
```

生成：`math.dll`

##### 链接库

```cmake
target_link_libraries(
    app
    math
)
```

##### 编译选项

开启 C++20：

```cmake
set(CMAKE_CXX_STANDARD 20)
```

现代推荐：

```cmake
target_compile_features(
    app
    PRIVATE
    cxx_std_20
)
```

### 包管理器

C++ 第三方依赖可能以不同形式存在：

- 只有头文件的库；
- 需要从源码构建的库；
- 预编译的静态库或动态库；

##### 相关文件

###### `vcpkg.json`

> 项目清单（Manifest）。描述项目信息、依赖等。

最简格式：

``` json
{
    "dependencies": []
}
```

> 已经合法，表明项目中无依赖

完整结构：

``` json
{
    "name": "my-project",
    "version": "1.0.0",
    "description": "Example project",
    "homepage": "https://github.com/example/my-project",

    "dependencies": [
        {
            "name": "fmt",
            "version>=": "11.0.0"
        },
        {
            "name": "opencv4",
            "features": [
                "core",
                "imgproc",
                "highgui"
            ]
        },
        "spdlog",
        "eigen3"
    ]
}
```

- `name`：项目名称。对于 application 非必须；对于 lib 建议填写。
- `version`：项目版本。对于 lib 建议填写。
- `description`：描述。无编译作用。
- `homepage`：项目主页
- `dependencies`（重点）：依赖库列表。可以直接写字符串，高级写法可以写对象，指定 version、features等信息。

###### `vcpkg-configuration.json`

> 包源配置。描述**从哪里获取这些依赖、使用哪个版本库**（仓库配置）。

默认：

``` json
{
    "default-registry": {
        "kind": "builtin",
        "baseline": "xxxxxxxxxxxxxxxxxxxxxxxx"
    }
}
```

> 只有一个配置，使用默认包源（官方 vcpkg 仓库）

- `baseline`：仓库某一次 Git 提交（commit）的哈希值。即进行版本锁定。

##### 基本使用

###### 0. CMake 项目中的配置

若要在 CMake 项目中 [使用](https://learn.microsoft.com/zh-cn/vcpkg/users/buildsystems/cmake-integration)vcpkg，需要将 `CMAKE_TOOLCHAIN_FILE` 变量设置为使用 vcpkg 的 CMake 工具链文件。 vcpkg 工具链位于 `%VCPKG_ROOT%/scripts/buildsystems/vcpkg.cmake`中，其中 `%VCPKG_ROOT%` 是 vcpkg 安装路径。

使用以下任一方法设置工具链文件：

- 在 `CMakePresets.json` 文件中设置 `CMAKE_TOOLCHAIN_FILE`。
- 在 CMake 配置调用中将 `-DCMAKE_TOOLCHAIN_FILE=<path/to/vcpkg>/scripts/buildsystems/vcpkg.cmake` 作为参数传递。
- 请在 `CMAKE_TOOLCHAIN_FILE` 文件中第一次调用 `project()` 之前，设置 `CMakeLists.txt` CMake 变量。

###### 初始化

``` shell
vcpkg new --application
```

最常用，创建应用项目。执行后添加`vcpkg-configuration.json`和`vcpkg.json`文件。

若创建库项目：

``` shell
vcpkg new --name mylib --version 1.0.0
```

参数：

- `--name`：初始化的项目名称
- `--version`：初始化的项目版本

###### 搜索

``` shell
vcpkg search [options] [query]
```

按名称和说明搜索可用的包。

搜索对所有可用的包名称和说明执行不区分大小写的搜索。 结果以表格格式显示。

###### 添加库

``` shell
vcpkg add port [options] <port-name>...
```

`vcpkg add port` 命令可以通过将新的包依赖项添加到 C++ 项目来更新 `vcpkg.json` 清单文件。

可以指定要添加的一个或多个端口名称。 还可以定义要作为依赖项包含的端口的特定功能。 然后，清单 (`vcpkg.json`) 将更新以反映这些更改。

示例：

``` shell
vcpkg add port fmt sqlitecpp zlib
```

> 添加 fmt、sqlitecpp、zlib 三个库

``` shell
vcpkg add port sqlitecpp[sqlcipher]
```

> 添加 sqlitecpp 库，features 为["sqlcipher"]

``` shell
vcpkg add port fmt --version=10.2.1
```

> 添加 fmt 库，版本 >= 10.2.1。若要精确固定版本，则到`vcpkg.json`删除对应的`>=`。

###### 删除库

严格执行`vcpkg.json`的清单模式暂不支持指令删除，需自行编辑`vcpkg.json`。

#### 单文件轻量编译配置

> 适合学习语法/刷题

##### 1.新建工程文件夹，用 VS Code 打开并信任

##### 2.建立 `build.bat`

> 每次编译时调用该脚本

新建一个`environment`文件夹，在其内建立一个 `build.bat`文件。

````file
```
└── 📁environment
    ├── build.bat
```
````

内容：

``` bat
@echo off

if "%~1"=="" (
    echo Usage: build.bat filename.cpp
    exit /b 1
)

rem 初始化 MSVC 编译环境
call "%ProgramFiles(x86)%\Microsoft Visual Studio\Installer\vswhere.exe" ^
 -latest ^
 -products * ^
 -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64 ^
 -property installationPath ^
 > "%TEMP%\vs_path.txt"
set /p VSROOT=<"%TEMP%\vs_path.txt"
call "%VSROOT%\Common7\Tools\VsDevCmd.bat" -arch=x64

rem 创建 build 目录
if not exist "%~dp0build" (
    mkdir "%~dp0build"
)

clang-cl ^
/std:c++20 ^
/EHsc ^
/Zi ^
/Fe:%~dp0build\%~n1.exe ^
%1
```

> 大意：找到最新的，x64的VS环境并运行 -> 创建 build 目录 -> 运行编译命令

- 若 Microsoft Visual Studio 没有安装在默认的 C:\Program Files (x86)\Microsoft Visual Studio，需自行将`%ProgramFiles(x86)%`改为安装的地址。

# 嵌入式开发环境

嵌入式开发（以 STM32 为例）与通用软件开发有一定不同。

## 嵌入式开发环境概述

在上文基础上，针对嵌入式情景，进行分层如下：

### 第一层：目标芯片与外设

嵌入式项目的最终运行目标不是 " Windows x64 " 这样的通用计算机平台，而是某个具体的 MCU （微控制器）型号，如 STM32F103C8T6 。

#### 芯片与处理器内核

STM32 是 意法半导体 公司推出的 **32 位 ARM Cortex-M 内核微控制器系列**。Cortex-M系列处理器内核是由 Arm 公司设计的，意法半导体公司购买相应处理器IP并在其基础上设计芯片。一颗 STM32 芯片总体上可以区分为 **处理器内核** 与它周围**集成的存储器、总线、外设、时钟、电源和调试系统**。具体需要查阅**芯片文档**。

``` STM32 MCU
STM32 MCU
├── Cortex-M处理器内核
│   ├── CPU与寄存器
│   ├── NVIC
│   ├── SysTick
│   ├── 调试单元
│   └── FPU、MPU、Cache等可选单元
├── 片上存储器
│   ├── Flash
│   ├── SRAM
│   ├── CCM/TCM
│   ├──备份 SRAM
│   └──系统 Bootloader所在的系统存储区
├── 片上总线
│   ├── AHB/AXI
│   ├── APB
│   └──总线矩阵
├── 系统功能
│   ├── RCC时钟与复位
│   ├──电源管理
│   ├──看门狗
│   ├──DMA
│   └──中断和外部事件控制
└── 片上外设
    ├── GPIO
    ├──定时器与PWM
    ├── ADC、DAC、比较器
    ├── UART、SPI、I²C
    ├── CAN、USB、Ethernet
    └──其他系列专用外设
```

- 指令集架构

  上文提到指令集架构时，简单举了x86、Arm两个例子。实际上，Arm 是一个不断演进、并针对不同用途分支的**指令集架构家族**，内部仍有细分。Cortex-M 系列处理器内核名字中的 M 即 Microcontroller，表示该系列定位面向低功耗、低成本 MCU 。其对应的具体**指令集架构**包括 Armv6-M（Cortex-M0）、Armv7-M（Cortex-M3）等等。

- 芯片

  两颗芯片即使使用相同处理器内核，其存储器布局、外设、寄存器地址和引脚配置也可能不同。编译器生成指令时主要依据处理器内核、指令集、FPU和ABI，而完整工程还必须指定具体MCU型号，以选择正确的设备头文件、启动文件、链接脚本和外设配置。

---

#### 外设

外设，即外部设备，是一个相对概念。例如显示器是 PC 的外设。在嵌入式语境中，大体上可以分为三种：

- **片上外设**

  即芯片上的外设，集成在 MCU 芯片内部，在上节有提到。包括 GPIO、定时器等。

- **板上外设**

  即 PCB 板上的外设，位于 STM32 芯片之外，但焊接在同一块控制板上。可能有：

  - 外部晶振

  - CAN收发器（部分芯片在内部有集成，那就是片上外设）
  - 陀螺仪
  - USB 芯片
  - ······

  > - **BSP（Board Support Package，板级支持包）**
  >
  >   当你进一步学习，学到工程架构时，就会发现许多工程都会有一个 BSP 层：
  >
  >   <img src="./images/image-20260727220804657.png" alt="image-20260727220804657" style="zoom: 50%;" />
  >
  >   简单来说，BSP 对一块控制板进行抽象，封装出需要使用的功能外设，包括片上外设与板上外设。这在代码层面实现了解耦，当需要更换芯片/控制板时，只需要对 BSP 层进行适配，就可以使得上层应用代码得以运行，轻松实现迁移。

- **外围器件**

  位于控制板之外，通过线缆、连接器或总线与控制板连接：

  - 电机、电调、舵机；
  - 遥控接收机；
  - 裁判系统；
  - 板外陀螺仪
  - ······

---

---

### 第1.5层：ABI

在 STM32 开发中最底层最重要的 ABI 就是 Arm 平台定义的 **Arm EABI 体系** 及其 **过程调用规范 AAPCS** 。其地位可以类比为 Windows x64 上的 Microsoft x64 ABI 。

> Arm EABI 是总规范，AAPCS 是其中最核心的部分。

AAPCS规定函数调用时的参数传递、返回值、寄存器保存和栈使用等通用规则。C、C++、Rust和汇编等生成的代码，只要需要互相调用，就必须遵守兼容的过程调用规则。

C接口模型简单、稳定，且 C语言 是主要与默认语言，经常作为跨语言的公共边界 ，C ABI 规定语言之间如何暴露函数接口。

在 C ABI 上层是高级语言 ABI （若存在），如 C++ ABI，解决高级语言自身特性的二进制表达。C++ 等高级语言函数想要被 C 调用，必须通过`extern "C"`来暴露接口，其意义就是告知编译器使用 C ABI。

从而，不论使用什么语言开发，最终通常收敛到：

``` 
C++ / Rust / 其他语言内部ABI
             ↓ 显式FFI边界
          C兼容接口
             ↓
     Arm ABI / AAPCS
             ↓
        Arm机器指令
```

编写汇编时，必须手动遵守相应 ABI 。

---

---

### 第二层：语言实现与交叉编译工具链

#### 语言实现

STM32 工程主要使用：

- C				主要与默认语言
- 汇编（Assembly）    负责少量底层启动和处理器相关代码，以及高性能要求代码
- C++                            负责复杂工程的上层逻辑

> - 为什么 C语言 如此特殊
>
> C语言之所以在嵌入式开发中占据统治地位，主要在于它恰好处于硬件和高级软件之间的一个特殊抽象层。既不像汇编那样高度绑定具体的 CPU ，又不像 Python 那样依赖重运行时。对于 MCU 这种资源极其有限的平台，C 提供了最好的平衡。
>
> 早期 MCU ，包括现在部分生态极度落后的部分 MCU 大量使用汇编，虽然有极致性能等优点，但其不可移植性、编写/维护困难性决定了它无法成为合格的工程语言。
>
> 而使用 C语言 封装后，在易于编写的同时：
>
> - 仍然接近硬件，几乎等价于 “可移植汇编”
> - 运行时轻
> - ABI 简单稳定，成为跨语言桥梁
>
> 随时间的发展，其嵌入式底层生态的地位愈发稳固，工具链愈发成熟，几乎所有 MCU 平台都以 C语言 为底层开发的核心语言。

---

#### 交叉编译工具链

**交叉编译：在一种计算机平台（Host）上运行编译工具，生成另一种计算机平台（Target）能够运行的程序。**

也就是说，在 Windows/macOS 平台上，开发嵌入式 Arm 程序，进行的编译就是交叉编译。

``` 
	C/C++源码
      ↓编译器
	目标文件 (.o)
      ↓链接器
	ELF固件
      ↓转换
	BIN/HEX文件
      ↓烧录
	STM32
```

C/C++ 的三种主流编译工具链，除了 MSVC 只针对 Windows，GCC 与 Clang 体系都支持 Arm 平台，也都适合 STM32 开发。鉴于 GCC 在该领域的时间积累、调试生态，在这里主要介绍 GCC 的交叉编译工具链：**Arm GNU Toolchain**，包括：

- `arm-none-eabi-gcc`：C 编译器
- `arm-none-eabi-g++`：C++ 编译器
- `arm-none-eabi-as`：汇编器
- `arm-none-eabi-ld`：链接器
- `arm-none-eabi-ar`：静态库工具
- `arm-none-eabi-objcopy`：二进制工具
- `arm-none-eabi-gdb`：调试器
- ······

名称中，`arm`表示目标平台；`none`表示裸机；`eabi`表示遵循 Arm EABI 。

### 第三层：构建系统与构建器

哪怕最简单的 STM32 程序也包含大量不同来源、不同语言和不同编译选项的文件，必须有构建系统与构建器辅助编译。

得益于 ST 官方的生态建设，现代STM32开发正在逐步加强对CMake等通用构建系统的支持。队内统一采用CMake描述工程，并由Ninja或Make构建器执行构建。

### 第四层：源码与依赖

STM32 工程的源码与依赖通常有以下几部分：

#### RTOS（可选）

实时操作系统（RTOS, Real-Time Operating System），代表如 FreeRTOS ，也是操作系统的一种，可以提供任务管理、CPU调度等服务，符合操作系统的核心定义：

> **负责管理计算机资源，并为应用程序提供运行环境的软件系统。**

相对 Windows 这样的**通用操作系统**，它缺少文件系统等功能。更核心在于，它的构建方式更接近库，将源码加入单个工程当中，而非独立安装与启动。

不同于普通计算机必须安装操作系统，在 MCU 上 RTOS 不是必须的，根据需求来决定是否使用。

---

#### 其他中间件，如FATFS文件系统（可选）

---

#### CMSIS

**CMSIS（Common Microcontroller Software Interface Standard）**是Arm制定的一套软件接口标准和基础软件组件。目的是为不同厂商、不同Cortex-M芯片提供统一的内核访问方式、设备文件组织方式和常用软件接口。包括：

- CMSIS-Core；
- CMSIS-Device；
- CMSIS-DSP；
- ······

CMSIS-Core标准文件主要由Arm提供，具体芯片的设备文件则由ST等芯片厂商按照CMSIS规范提供。

---

#### 标准库 & HAL库

标准库和HAL库都是 ST 在 CMSIS-Device 基础上建立的外设驱动/抽象层。标准库已经被弃用，HAL 是现代工程的主要路线。

---

#### 工程源码

与普通 C/C++ 工程不同的是，STM32 工程一般不直接安装第三方库，也没有类似 vcpkg 的库管理工具。要使用他人写好的库（如OLED驱动），一般要先针对目标的芯片进行一定改写适配，且源文件的放置与结构安排也要根据项目需求具体设计。

### 第五层：开发工具

#### STM32CubeMX

**STM32CubeMX**是ST官方提供的STM32芯片配置与代码生成工具。它通过图形化界面帮助开发者配置芯片资源，并生成相应的初始化代码和工程文件。它大大简化、标准化了工程芯片外设相关资源的配置。

与此同时，它还整合了 FreeRTOS 等组件，并支持了 CMake 构建配置。是现代 STM32 开发最常用的工具之一。

---

#### 编辑器 & IDE

VS Code 是现代化的、队内统一的开发工具。与此同时，开发 STM32 常用的 IDE 还有：

- Keil：历史悠久，界面古老，但出于其深厚的积累、高度集成的环境，仍在被大量使用。
- CLion：专注于C/C++的通用IDE，代表以CMake为基础的现代C/C++。

  ### 1.安装 STM32CubeMX

到 [ST 官网](https://www.st.com.cn/zh/development-tools/stm32cubemx.html#section-get-software-table) 下载安装包：

  <img src="./images/屏幕截图 2026-07-26 092828.png" alt="屏幕截图 2026-07-26 092828" style="zoom:50%;" />

下载需要 ST 账号，自行注册登录。

解压并打开安装包安装。

### 2.安装 VS Code

到 [Visual Studio Code 官网](https://code.visualstudio.com/)，点击`Downloal`下载安装。打开并点击左栏第五项扩展，搜索`Chinese`，找到并安装中文插件。

### 3.新建配置文件

左下设置	->	配置文件	->	配置文件

<img src="./images/屏幕截图 2026-07-26 095504.png" alt="屏幕截图 2026-07-26 095504" style="zoom:50%;" />

新建配置文件	->	输入名称	->	创建

<img src="./images/屏幕截图 2026-07-26 095727.png" alt="屏幕截图 2026-07-26 095727" style="zoom:50%;" />

切换到新建的配置文件

<img src="./images/image-20260728080605361.png" alt="image-20260728080605361" style="zoom:50%;" />

### 4.安装插件

在扩展搜索并找到：`STM32CubeIDE for Visual Studio Code`：

<img src="./images/屏幕截图 2026-07-26 100042.png" alt="屏幕截图 2026-07-26 100042" style="zoom:50%;" />

这是一个扩展包，含15个扩展。安装该扩展包。

安装完成后，发现左栏多了两项。点击最后一项`STM32Cube`，点击 STM32CUBE BUNDLES 管理器 系统 右边的清单按钮。

<img src="./images/image-20260728081441143.png" alt="image-20260728081441143" style="zoom:50%;" />

发现插件帮我们安装好了一系列环境，包括：

- `cmake`
- `gnu-gdb-for-stm32`：gdb 调试器
- `gnu-tools-for-stm32`：GCC 交叉编译工具链
- `ninja`
- `st-arm-clang`：Clang 系交叉编译工具链
